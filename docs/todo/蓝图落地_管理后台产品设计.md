# 工地巡场 · 管理后台产品设计（v1）

> **读者**：产品 / 设计 / 前端 / 后端 / 驻场
> **依据**：`flutter_app/FEATURE_INVENTORY.md`（功能基线）· `蓝图落地_数据与录入入口（团队说明）.md`（数据来源）
> **设计原则**：**不过度设计**。后台第一版只解决一件事 —— **App 拿不到的那批数据，从哪来**。
> **凡是 App 已经能做的，后台一律不做。**
>
> **状态：范围讨论中。** 页面级设计（信息架构 / 逐页设计）**待范围定稿后再补**，本文暂不写 —— 避免每讨论一次就改一遍。

---

## 1. 定位

App 是现场端，它注定产生不了三类数据：

| 缺的数据 | 为什么 App 录不了 | 本版 |
|---|---|---|
| **项目档案**（项目 / 参与方 / 里程碑） | 项目开工时才有，且是全院性信息，不是某个驻场的私有数据 | ✅ 做 |
| **图纸与底图**（文件 / 版本 / 校准） | 动辄几十 MB、要版本管理、要在大屏上标定坐标 | ✅ 做 |
| 全院共用配置（规范条款 / 验收门槛） | 一次配好全院共用，不该每个项目各录一份 | 暂不做（见 §3.2） |

前两类的共同特征是：**低频、权威、一次录好长期用**。

> **一句话定位：后台 = 项目的「初始化台」。**
> 项目开工前，先在后台把档案、图纸、人配齐；App 端此时才"有东西可看、有地方可打点"。

### 1.1 与 App 的职责边界

这条边界决定了后台为什么这么小：

| | 后台 | App |
|---|---|---|
| 负责 | 项目**开工前的样子** | 现场**正在发生的事** |
| 数据 | 档案 · 图纸 · 成员 | 缺陷 · 验收 · 量尺 · 巡场 · 报告 |
| 频次 | 一个项目用几次 | 每天用 |

**判断一个功能该不该进后台，只问一句**：这件事在现场做，是不是比在电脑前做更好？
是 → 归 App（如"标记缺陷"）；否 → 归后台（如"传一张 40MB 的图纸"）。

## 2. 用户与角色

| 角色 | 是谁 | 本版是否实测 | 在后台做什么 |
|---|---|---|---|
| **系统管理员** | 院 AI 中心 / 信息中心 | ✅ **实测** | **全权**：建号、建项目、配成员、传图纸、做校准、发布 |
| **项目成员** | 驻场工程师 / 专业负责人 | ✅ **实测** | 传图纸、做校准；查看项目档案 |
| 项目负责人 | 院内项目负责人 | 暂不单列 | 本版其职责**由管理员一并承担**，等角色真实分化再拆 |
| 施工方 | 施工 / 总包现场人员 | 不在本版 | 见 §3.2 |

**本次真实测试只覆盖两个角色：系统管理员 + 项目成员。**

第一版权限刻意做粗：**管理员全权，成员可传图纸与做校准，其余只读**。
不做权限点自定义 —— 现在只有两个角色在跑，把权限做细是纯浪费。

## 3. 范围

### 3.1 第一版做（7 件事）

| # | 能力 | 落在哪 |
|---|---|---|
| 1 | 登录 | 登录页 |
| 2 | **建号**（管理员手工建账号） | 用户管理 |
| 3 | 项目建档（基本信息 + 参与方 + 里程碑） | 项目列表 → 新建向导 |
| 4 | 项目成员与角色 | 项目详情 · 成员 |
| 5 | **图纸上传 → 出底图 → 校准 → 发布** | 项目详情 · 图纸 |

### 3.2 本版不做 · 未来规划

**A. 明确会做，只是不在本版**

| 项 | 为什么不在本版 |
|---|---|
| **施工进度「施工方免登录」分享页** | 要先建分享链接服务 + 免登录页，本版先不引入这条外部链路。**进度录入本身本版就做**（§3.1 第 6 项），只是第一版走后台登录态 → `source = admin`（身份可信）；v1.2 的免登录自报才是 `contractor`，两者**不得混标** |
| 规范条款与验收门槛 | 要先做规范库导入；且 AI 引用能力本身还没到可用状态 |

**B. 有理由进后台，等触发条件**

| 项 | 触发条件 |
|---|---|
| 专业负责人只读视图（缺陷反哺设计第一出口） | 项目成员数据积累起来（依赖本版第 4 项） |
| 跨项目缺陷与报告汇总视图（只读统计，不编辑） | 有 3 个以上真实项目在跑 |
| 数据看板 | 有真实数据可统计之后 |
| 消息通知 | 出现明确需要通知的业务动作 |
| 批量导入项目 / 用户 | 项目数超过手工可维护的量级 |
| 多租户 / 部门树 | 出现第二个使用单位 |
| DWG 在线预览 | 由 CAD 独立项目的进度决定 |
| 后台移动端适配 | 出现"必须在手机上看后台"的真实场景 |

**C. 版本节奏**

| 版本 | 内容 |
|---|---|
| v1.1 | 图纸批量上传 · 成员按专业过滤 |
| v1.2 | 施工进度**免登录分享页**（v1 已支持后台录入） |
| v2.0 | 规范条款与门槛 · 专业负责人只读视图 · 跨项目汇总 |

## 4. 与客户端的对接：接得住吗

### 4.1 字段映射

后台每一样录入，都能在客户端找到消费方 —— 这是"接得住"的证据：

| 后台入口 | 主要字段 | App 端谁在读 |
|---|---|---|
| 项目档案 | name / client / location / status / siteArea / floorArea / beds / concept | 引导页选项目、首页项目卡、报告封面 |
| 参与方 | role / org / contact / title | 首页项目信息、报告抬头 |
| 里程碑 | name / date / done | 首页进度时间轴、报告"施工进度"章节 |
| 项目成员 | 用户 + 项目内角色 | **可见性判定**（登录后能看到哪些项目） |
| 图纸 | 图纸名 / 专业 / 楼栋 / 楼层 / 版本 | 图纸 tab 目录、拍照验收选部位、量尺选图纸 |
| **底图 + 校准** | 底图文件 + 校准参数 | 图纸查看、图上打点、量尺图纸侧取值、巡场防穿墙 |

> 施工进度、门槛、规范条款对应的 App 消费点（首页进度、量尺判定、AI 引用）**本版暂不启用**，接口预留即可。

### 4.2 三个必须先对齐的结构点

| # | 结构点 | 现状 | 要求 |
|---|---|---|---|
| 1 | **图纸版本** | 客户端按 `drawingKey` 存校准，不按版本 | 后台发布新版本时，客户端要能感知"该重拉底图、重校准" |
| 2 | **楼层是图纸的属性** | 客户端 `Floor` 列表 = 图纸目录，`Floor.name` 装的就是图纸名 | 后台不单独建楼层；楼层标签随图纸走（**已同步**：`BACKEND_ARCHITECTURE.md` §7.3 取消 `floors` 表） |
| 3 | **校准是项目资产** | 客户端校准存本机（每人一套） | 后台发布的那份为默认值；App 端本地微调不覆盖它 |

### 4.3 客户端要配合改的地方（后台之外，但必须同批做）

1. **项目列表改从后端拉** —— 现在是 2 个写死的常量。
2. **登录改真实账号** —— 现在是点一下即登录、写死 demo 用户。
3. **图纸列表与底图改从后端拉** —— 现在指向打包在 App 里的 11 张预置图。

> 这三条不改，后台录得再对，App 也接不上。**它们是"接得住"的前提，不是可选项。**

## 5. 关键流程

### 5.1 项目上线（首次）

```
管理员建项目 → 填基本信息 / 参与方 / 里程碑
  → 上传图纸（PDF）→ 系统出底图 → 点两点校准 → 发布
  → 添加成员
  → 成员在 App 登录 → 看到这个项目 → 能看到图纸 → 能打点
```
**这条链跑通 = 后台第一版成功。**

### 5.2 图纸改版

```
上传新版本（V2.0）→ 重新校准（旧校准标记"已过期"）
  → 发布 → App 端提示"图纸已更新，请重新加载"
  → 旧版本锁定只读，历史缺陷仍指向旧版本（不错位）
```

### 5.3 账号开通

```
管理员建号（姓名 + 手机号 + 单位）→ 告知初始密码
  → 用户登录 App → 由管理员在项目里加入成员
  → 该用户才能看到项目
```
> 注意顺序：**建号 ≠ 能看项目**。可见性由项目成员关系决定。

## 6. 第一版验收标准

用一段可现场演示的脚本验收，逐条可判真假：

| # | 步骤 | 通过标准 |
|---|---|---|
| 1 | 管理员登录后台 | 能登录；错误密码被拒 |
| 2 | 新建一个项目 | 走完建档流程，项目出现在列表 |
| 3 | 上传一张 PDF 图纸并发布 | 底图能预览；未校准不允许发布 |
| 4 | 在底图上点两点、输入实际距离 | 校准状态变为"已校准" |
| 5 | 添加 2 名成员 | 成员列表可见，角色正确 |
| 6 | App 端登录该成员账号 | **只看到这个项目**（不是全部） |
| 7 | App 端打开图纸 | 看到的是**后台刚上传的那张**，不是预置图 |
| 8 | App 端在图纸上打点 | 点位落在图纸正确位置（校准生效） |
| 9 | 在后台按 B4 节点回填一条施工进度 | 能保存并回显；该条 `source = admin`，界面**不**标注「施工方自报」 |

**9 条全过 = 后台第一版达标。**

## 7. 边界与红线

| # | 红线 | 原因 |
|---|---|---|
| 1 | **没有版本号的图纸不允许发布** | 图纸一改版，无版本的历史坐标全部静默错位 |
| 2 | **发布是显式动作，不是上传即生效** | 成员正在用旧图打点，中途换底图会造成新旧混用 |
| 3 | **不做自动坐标迁移** | 算法不可靠且不可解释；宁可让人重校 |
| 4 | **后台不碰业务数据** | 缺陷、验收、报告归 App；两边都写同一张表必然冲突 |
| 5 | **后台不做 AI 结论的最终裁决** | AI 只出建议，人确认后才生效（与 App 端一致） |

---

## 附：本版明确的 5 个产品决策

1. **后台 = 项目初始化台**，不是第二个管理大屏。
2. **不建楼层表**，楼层是图纸名解析出的标签。
3. **只收 PDF / 图片**，DWG 交给设计院出图流程。
4. **校准在后台做两点标定**，App 端高级校准保留但以发布版为准。
5. **发布是显式动作**，上传 ≠ 生效。
