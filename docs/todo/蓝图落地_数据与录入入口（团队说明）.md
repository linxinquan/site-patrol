# 蓝图落地 · 数据来源与录入入口

> **读者**：项目组全体（产品 / 设计 / 前端 / 后端 / 驻场）。
> **用途**：说清一件事 —— **系统里的每条数据，由谁、在哪个端、什么时候录进来**。
> **基线**：`flutter_app/FEATURE_INVENTORY.md`（功能事实源）。本文档只谈数据与入口，不谈界面细节。
> **状态**：设计结论，可直接作为开发依据。

---

## 0. 一页结论

**① 平台型数据（项目 / 用户 / 图纸 / 参与方 / 楼层）现在 100% 是写死的常量，大约 1,366 行。
它们不是"接了后端就会有"，而是"必须先把录入通道建出来"。**

**② 业务型数据（缺陷 / 验收 / 量尺 / 量房 / 巡场）数据本身是真的、逻辑也跑得通，
但全部存在手机本机（Hive / localStorage / 本地文件）—— 换台设备就看不到，对团队业务等于无效。
这类补后端即可复活，界面不用重写。**

**③ 产品定位里最值钱的两步 ——「责任判断」和「缺陷知识库」—— 在数据模型里一个字都没有。
全库搜不到 `liability` / `clause` / `specRef`。这不是数据假，是这条链还没开始建模。**

一句话落到开发上：**先把"事实"存对，再让"AI"说话。**
现在不是模型不够聪明，是 `severity`（严重度）、`clause`（规范条款）、`坐标版本` 这些**事实字段根本不存在**，模型再准也无处可写。

## 1. 数据现状：三类，处理方式完全不同

| 类别 | 判定 | 涉及数据 | 处理方式 |
|---|---|---|---|
| **平台档案类** | 🔴 完全缺失（无模型、无入口） | 组织 · 用户 · 项目 · 参与方 · 里程碑 · 楼层 · 图纸 · 热点 · 拍照锚点 | **要新建录入通道** |
| **现场业务类** | 🟡 有数据，但本机私有 | 缺陷 · 验收记录 · 量尺 · 量房 · 巡场 · 打卡 · 报告归档 · 媒体文件 | **补后端即可复活** |
| **差异化资产类** | 🔴 零起点 | 规范条款库 · 责任判据 · 整改建议库 | **要新建模型** |

**判断标准很简单**：数据只存在本机 = 换台手机就看不到 = 对真实业务无效。

### 三处必须单独点出的问题

| 问题 | 现状 | 影响 |
|---|---|---|
| **取证链是断的** | `imageSha256()` 定义了但全项目从未调用；`Defect.photoHash` / `watermarkSerial` 有字段、有序列化、但没有任何写入方 | 水印上烧的凭证号**只存在于图片像素里，数据库查不到** —— 出纠纷时无法自证 |
| **GPS 不是设备定位** | 拍照时用户从 5 个写死的点位里**手选一个**，再烧进水印 | 这不构成位置证据 |
| **校准不绑版本** | 校准参数按图纸名存，不按版本存 | 图纸一改版，历史坐标**静默错位**（界面不报错，只是指到别的房间） |

## 2. 真实数据只有 5 种生产方式

25 个数据实体，不该有 25 条来源，只有 5 种。每种的写入路径、频次、一致性要求完全不同 —— 混在一起就是现在"到处是 mock"的根因。

| 类型 | 特征 | 包含数据 | 写入路径 | 频次 |
|---|---|---|---|---|
| **① 组织与档案** | 低频、权威、一次性 | 组织 · 用户 · 项目 · 参与方 · 里程碑 | 后台管理页 / Excel 导入 | 项目开工时 |
| **② 图纸与底图** | **版本化**、文件型、携带坐标系 | 图纸 · 图纸版本 · 楼层 · 热点 · 校准参数 | 出图流程 → 上传 OSS → 版本表登记 | 每次改版 |
| **③ 现场采集** | 高频、**离线**、带时空戳 | 缺陷 · 验收记录 · 量尺 · 量房 · 巡场 · 打卡 · 照片 | 设备采集 → outbox → 直传 OSS → 落库 | 每天 |
| **④ AI 推理** | 概率性、**必须可回放** | 缺陷识别 · 严重度 · 责任判据 · 规范引用 · 整改建议 | `ai_jobs` 记输入输出 → 人工确认 → 才写业务表 | 每张照片 |
| **⑤ 派生计算** | 可重算、**不单独维护** | 楼层进度 · 闭合率 · 修正率 · 时间轴 · 拍照锚点 | 服务端聚合 / 视图，**不算数据源** | 查询时 |

### 每类的硬约束

**① 组织与档案 —— 关键是"谁是数据的主人"**
没有后台能建项目，项目就只能永远是常量。必须先有管理后台，否则接不了第二个真实项目。
项目档案里的合同信息、参与方、进度计划，**院内生产系统（步天 adoa）本来就有 —— 能对接就不要手填**。

**② 图纸与底图 —— 全场唯一必须版本化的数据**
这是最容易埋雷的地方。**只要有一个坐标落库时不带 `drawing_version_id`，图纸一改版，历史上所有缺陷点位全部错位，而且是静默的。**
底图走对象存储，客户端按需取缩图；**不再往 assets 里塞预置图**。
校准参数跟着版本走，改版即失效重校 —— 这是要**主动提示用户**的，不是要自动兼容的。

**③ 现场采集 —— 唯一允许"先落本机"的一类**
工地断网是常态，这类数据的正确姿态是：**客户端是暂时的写入方，服务端是权威**。
- 客户端 ID 用 **ULID** 本地生成（不要用毫秒时间戳，多端会撞）—— **已落地**：
  `lib/core/utils/ids.dart` 的 `newId()`（26 位 Crockford Base32，同毫秒自增、时钟回拨不倒退），
  可写实体统一由 `SyncMeta.clientId` 携带，落库即作为服务端幂等键。
- 照片：压到长边 2048px → 直传对象存储 → 只把 key / hash 回传业务表。放弃 base64。
- GPS 必须从设备取。
- 所有写入先进 outbox，联网再推。

**④ AI 推理 —— 结论与事实必须分表**
现状是 AI 结果直接混进业务记录，模型一改版，历史数据就无法解释。
- 新增 `ai_jobs`：记模型 / prompt 版本 / 输入 hash / 原始返回 / 耗时 / 成本。
- AI 写的是**建议**（`liability_suggestion`），人确认后才写**结论**（`defect_reviews`）。
- **AI 永不直接改工单状态。**
- 当前视觉接口只返回缺陷名 / 描述 / 置信度 —— **缺严重度、缺规范条款候选、缺判据**，这些必须扩后端返回结构，前端补不了。
- **可回放是硬要求**：验收指标"责任判断人工修正率 < 30%"要靠 `ai_jobs` 与 `defect_reviews` 比对才能算出来，不落 `ai_jobs` 这个指标永远算不出。

**⑤ 派生计算 —— 现在的错是"把它当数据存了"**
楼层进度应是"已销项 / 全部缺陷"的查询结果，不该是手填常量。
拍照锚点应按"图纸版本 + 坐标"对缺陷聚类，不该是独立数据表。
> 时间轴对比已经在这么做（由缺陷派生），**这是全项目最正确的一处设计，其余派生数据应照它改。**

## 4. 后台端的形态

**5 个页面 + 1 个流程**（**免登录进度填报页推迟到 v1.2**：第一版进度由后台登录态录入）。

| 页面 | 承载入口 | 谁用 |
|---|---|---|
| 登录页 | — | 全部 |
| 用户与邀请 | A2 | 超管 |
| 项目管理（列表 + 新建） | B1 / B2 / B3 / B4 | 管理员 / 项目负责人 |
| **项目详情**（成员 / 图纸 / 进度 / 门槛） | B6 / B7 / C1 / C2 / C3 / C4 | **全部项目成员** |
| 规范与模板库 | A1 / A3 / A4 / **A5 专业字典** | 院质量中心 |
| （流程）**上传 → 出底图 → 校准 → 发布版本** | C1 → C2 → 发布 | 项目成员 |
| **免登录进度填报页**（**v1.2**） | C4（v1.2 部分） | 施工方（无账号） |

### 两条实现约定

1. **上传一律走"客户端直传对象存储"，不经服务器中转。**
   页面先调服务端拿预签名上传地址（10 分钟有效）→ 直传 → 调接口登记。理由是图纸文件动辄几十 MB，服务器中转会直接顶爆网关的体积限制。C1 图纸、C4 进度照片都适用。
2. **服务端不做缩略图。**
   列表图 / 预览图一律用对象存储的实时图片处理参数出图。免掉一个依赖，也免掉工地照片量大时的第一个性能瓶颈。

### 一条必须先改的结构问题

**所有入口必须挂在「项目」下面。**
现在点位、图纸、楼层都是**全局常量数组**，与项目没有归属关系。不先改这个，后台建了项目也挂不上数据。

---

## 5. 三条最容易踩的坑

1. **"上传"与"校准"必须是同一个流程的两步。** 拆开则第二步行内 90% 没人做。
2. **图纸改版要"发布"，不是"上传即生效"。** 旧版锁只读 + 提示重锚，不做自动坐标迁移。
3. **App 端要能感知版本变化。** 否则驻场用旧底图打点，坐标直接错，且不会报错。

---

## 6. 数据结构必须一次做对的 5 条

1. **ID 链要闭合**：`项目 → 图纸版本 → 世界坐标 → 验收记录 → 缺陷 → 媒体 → 报告`。
   现状断在"验收记录"与"缺陷"之间 —— 只有单向弱引用，报告归档又是第三套元数据。三条链必须能互相追溯。
2. **坐标必须绑版本**：所有坐标与校准参数都必须带 `drawing_version_id`。
3. **取证必须落库**：照片 hash + 凭证号 + GPS + 拍摄时间四项入库，不能只烧在图片上。
4. **AI 只出"建议"**：建议与结论分表；置信度低于 0.9 或涉及强制性条文时**强制人工复核**；**低置信判定绝不直接生成变更单 / 整改单**。
5. **写操作全部可离线**：客户端 ULID + outbox，服务端权威。**不引 CRDT** —— 工地数据是任务型，不是协同编辑型。

> 另有一条扩展性约束：**不要把"设计院专属语义"写死进数据库**。缺陷分类、房间用途这类枚举要留可扩展位，否则将来做平民化产品要迁移。

## 7. 数据产权与角色边界

「参与方」（甲方 / 设计院 / 监理 / 施工 / 总包）现在**只是一张展示用的通讯录**，没和任何业务数据挂钩。但真实业务里：

- 谁写的缺陷、谁能看到、谁只能看到自己单位的 —— **由参与方关系决定**；
- 「整改回复」天然属于施工方，「责任判定」天然属于设计院。

因此 **参与方必须升格为"项目成员 + 权限点"**。它同时承担两件事：
① App 端"登录后能看到哪些项目"的唯一依据；② 权限边界的挂载点。

**实施顺序遵循既定铁律：先做只读角色（专业负责人），后做写入角色。**
院内角色拓展回报率最高的是**专业负责人只读视图**（开发量最小，且是"缺陷反哺设计"的第一出口），它的前提正是这张成员表。

## 8. 缺口分级与落地顺序

### P0 —— 不补则连一个真实项目都开不了

| 缺口 | 现状 | 补法 |
|---|---|---|
| 账号与鉴权 | 4 个 mock 用户，登录直写本地会话，无密码无令牌 | 组织 / 用户 / 成员表 + 邀请制 + JWT |
| **AI 路由无鉴权** | 接口裸奔，任何人可消耗额度 | 网关侧鉴权 + 配额（**第 1 周，属止血**） |
| 项目档案录入 | 2 个写死的项目 | 项目表 + 管理后台 |
| 图纸版本化 | 11 张预置图，无版本 | 图纸表 + 版本表 + 对象存储 |
| 业务数据落库 | 3 套本地数据互不相通 | 统一缺陷 / 验收 / 媒体表 |
| 媒体托管 | 本地文件；Web 刷新即丢 | 直传对象存储 + hash 校验 |
| 客户端仓库层 | 13 个方法中 11 个未实现 | 后端就绪后逐个实现 |

> **重要口径**：**P0 的真实工作量是"业务数据 CRUD + 后端"，不是那 7 个模块。**
> 约 8,900 行界面已经写完，接上数据即复活，**不要重复计工期**。这 7 个模块全卡在同一处，后端一补它们同时可用。

### P1 —— 决定"能不能真用"与"护城河成不成立"

责任判断链（规范条款 + 建议 + 复核）· 规范条款库与召回 · AI 结果结构化（严重度 / 置信度落库）·
取证链闭环 · GPS 真实化 · 巡场三处半接线修复 · 量尺口径统一 · 墙线资产 · **离线同步（生死线）**

### P2 —— 反哺与外部采信

跨项目缺陷知识库 · 责任判据沉淀 · 角色只读视图 · 报告正文归档（现在只存元数据）

### 落地顺序

```
第 1 周    鉴权 + 组织 / 用户 / 项目 / 成员表        ← 止血 + 让"项目"能建
第 2–3 周  图纸版本表 + 对象存储 + 媒体表            ← 坐标与文件的地基
第 4 周    缺陷 / 验收记录 CRUD                     ← 客户端空方法变实
第 5 周    实现客户端仓库层 11 个方法                ← 7 个模块同时复活
第 6 周    outbox 离线写入                          ← P1 生死线
之后       规范条款库 / 责任判据 / AI 任务表          ← 护城河
```

**演示最小切片**：`登录 + 项目成员 → 图纸（含校准）→ 施工进度`。
这四样通了，"登录 App 看到自己项目的图纸和进度"就成立；**其余现场数据先继续走本机**，演示看不出差别，但能省掉同步引擎这个大坑。
