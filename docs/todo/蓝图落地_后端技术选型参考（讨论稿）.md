## 3. 三个候选

### 3.1 Node 22 + TypeScript 5 + Express 5（+ Prisma + Zod）

|            |                                                                                                                                                                                                      |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **优点**   | ① **AI 语料最厚**，生成与纠错最可靠（判据 #1 #2）② **Prisma**：schema 即文档 + 迁移自动 diff + 类型生成（判据 #3）③ 宝塔「Node 项目管理器」**路径已在跑**（判据 #4）④ 与现有网关同栈，排障资料可复用 |
| **代价**   | ① 共机多一套 Node 运行时（但**本来就在跑**）② 常驻内存比 Go 高些 ③ 弱类型惯用法容易漏错 → 必须靠 `strict` + Zod 兜住                                                                                 |
| **对我们** | **摩擦最小的一条**：卡住时最容易搜到答案，AI 也最会写                                                                                                                                                |

### 3.2 Python 3.12 + FastAPI（+ SQLAlchemy 2.0 / asyncpg + Pydantic）

|            |                                                                                                                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **优点**   | ① **Pydantic** 是做"AI 返回结构校验 + 半结构化解析"最顺手的工具（本项目明确要做这件事）② FastAPI 自动出 OpenAPI 文档，交接友好 ③ AI 语料同样很厚 ④ SQLAlchemy + asyncpg 成熟，jsonb 支持好 |
| **代价**   | ① 宝塔要装「Python 项目管理器」+ uvicorn/gunicorn 组合，**配置项比 Node 多**（判据 #4 最弱）② 运行时类型安全弱于 TS / Go ③ 共机多一套 Python 运行时                                        |
| **对我们** | 如果**院里有会长期写 Python 的人**（或我们自己愿意以 Python 为主），这条会反过来变首选                                                                                                     |

### 3.3 Go 1.23 + chi（或 gin）+ pgx

|            |                                                                                                                                                                                                                                                                                                     |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **优点**   | ① **部署最干净**：编译成单个静态二进制 → 宝塔的**进程守护（Supervisor）管理器**守护任意可执行文件即可，**不装运行时、不要语言专用项目管理器**（判据 #4 最强）② 常驻内存最小（十几 MB）③ 编译期强类型（判据 #3）④ `json.RawMessage` 最贴合"服务端不解析 jsonb"的设计 ⑤ 性能/并发强（对本项目无意义） |
| **代价**   | ① **AI 语料明显少**，生成质量与纠错都吃亏；写法也更啰嗦（错误处理冗长、无 ORM 一等公民）② **没有 Prisma 等价物**：迁移用 `goose` / `golang-migrate`，索引等要手写 SQL ③ 出错时社区答案最少 ④ 学习与排障成本最高                                                                                     |
| **对我们** | 技术属性最"干净"，但**与我们的两条主要判据（#1 AI 能准确写、#2 搜得到答案）方向相反** —— 适合"有人愿意投入学、且把共机影响最小看得最重"的情形                                                                                                                                                       |

### 3.4 附：为什么不建议用 Dart 写后端

它唯一真正的吸引力很硬：客户端模型 `toJson/fromJson` **本身就是落库契约**，若后端也是 Dart，
可以**共享同一份模型**，契约漂移归零，而且 app 与服务端只剩一种语言。

但障碍是实的：① `models/defect.dart` 依赖 `package:flutter/material.dart`（不是纯 Dart），想共享得先抽包；
② 没有 Prisma 等价物，服务端生态小（shelf / dart_frog / Serverpod）；③ 宝塔没有 Dart 项目类型，要 PM2 自定义脚本 + AOT 编译。

> **一个更省的做法**：如果将来"客户端与服务端字段不一致"真的成为反复出现的痛点，
> 该做的是把 `lib/data/models/` 抽成**无 Flutter 依赖的纯 Dart package**（顺带可导出 JSON Schema 给后端做校验），
> **而不是换后端语言** —— 收益类似，成本低一个量级。

## 5. 参考建议（**供讨论，不是定稿**）

**倾向：Node 22 + TypeScript + Express 5 + Prisma。**

理由按判据排序：

1. **#1 #2**：AI 最能写、出问题最搜得到 —— 这是"非专业后端 + AI 开发"团队的命门；
2. **#3**：Prisma 的"schema 即文档 + 迁移自动化 + 类型生成"等于**免费替我们查错**，正合本项目"客户端模型即契约"的形态；
3. **#4**：宝塔 Node 路径**已经在跑**（现有 AI 网关），运维动作是现成的；
4. 代价（多一套已在跑的运行时、内存高些）都可接受。

**次选：Python + FastAPI** —— 如果**院里会有 Python 工程师长期接手**，或者我们更看重
"Pydantic 对 AI 返回的校验体验 + 自动 OpenAPI 文档"，这条完全站得住。

**不建议作为首选：Go** —— 它在「部署最干净 / 内存最小」上确实最好，但这两点对我们不是主要痛点；
而它的短板（AI 语料少、无 Prisma 等价物、排障资料最少）**正好压在我们最痛的两条判据上**。

**什么情况会改变这个建议**：

- 出现一位**愿意长期投入的 Go 维护者** → Go 可以升为次选甚至首选（此时它的部署优势会真正兑现）；
- 院里确认有**会长期写 Python 的人** → Python 升为首选；
- 我们自己在讨论中发现"AI 语料"这条没想象中重要（例如主要靠我们自己写）→ 三条重新拉平，回到"谁的部署最省心"。

## 7. 数据库：为什么建议 PostgreSQL（与语言无关）

> 这条**不是偏好问题** —— 选错了会让离线同步**静默丢数据**。

### 7.1 数据形态

以**关系模型**为主（项目 → 图纸 → 缺陷 → 事件 → 回复 → 成员权限），
但有**大量半结构化字段**（客户端 `toJson()` 原样落库，服务端不解析几何）：

```
measure_sessions.items / calib        room_scans.walls / checks
patrol_records.track / checkins       projects.parties / milestones / measure_thresholds
drawings.hotspots                     captures.ai_result / confirmed_result
defects.tags / photos                 memberships.permissions
```

→ 需要一个**既能建外键关系、又能装 JSON 文档**的库。这一条直接排除 MongoDB（关联查询弱、无外键、事务能力受限）。

### 7.2 关键机制：同步变更流的序号分配

离线同步靠一张变更流表 + 游标：

```sql
changes(seq bigserial PK, project_id, entity, entity_id, op, changed_at)
-- 客户端只记一个游标，按 seq > cursor 拉增量
```

**陷阱**：`bigserial` 的**分配**严格递增，但**可见性由提交时间决定**。两个事务可能"先分配、后提交"：

```
T1  事务 A  nextval → seq = 100（未提交）
T2  事务 B  nextval → seq = 101，随后提交
T4  客户端拉取，读到 max(seq) = 101 → 游标推到 101
T5  事务 A 提交，seq = 100 才可见
T6  客户端从 101 继续拉 → 100 永远拉不到（静默丢一条变更，无任何报错）
```

**PostgreSQL 的解法（1 行）**：在写 `changes` 的同一事务开头取**事务级咨询锁**，让序号分配被串行化，
于是"分配顺序 ≡ 提交顺序"，`seq > cursor` 恢复正确：

```sql
SELECT pg_advisory_xact_lock(981001);   -- 事务结束自动释放，不会泄漏
INSERT INTO changes(project_id, entity, entity_id, op) VALUES (...) RETURNING seq;
```

代价：变更流写入被串行化。本项目写入 QPS 极低，**代价可忽略**。

**MySQL 为什么不行**：只有**会话级** `GET_LOCK()`，必须显式 `RELEASE_LOCK`；连接池下极易泄漏或误释放，
**没有可靠的写法**。这是"必须 PG"的最硬理由。

### 7.3 其它对本项目有实际影响的差异

| 项                           | PostgreSQL                                           | MySQL 8                                         | 我们用在哪                                  |
| ---------------------------- | ---------------------------------------------------- | ----------------------------------------------- | ------------------------------------------- |
| **数组类型 `text[]`**        | ✅ 原生 + GIN 索引                                   | ❌ 无原生数组                                   | `memberships.disciplines`（成员专业维度）   |
| **JSONB 一等类型 + GIN**     | ✅ 可索引、可 `@>` 包含判断                          | 🟠 JSON 需借生成列建索引，操作符能力弱          | `items` / `walls` / `track` / `ai_result` … |
| **部分索引**                 | ✅ `CREATE INDEX … WHERE deleted_at IS NULL`         | ❌ 无                                           | 全表软删，能显著压缩索引体积                |
| **`ON CONFLICT DO NOTHING`** | ✅ 幂等 upsert 的天然表达                            | 🟠 `INSERT IGNORE` 会吞掉所有错误（含数据截断） | `client_id` 幂等重发                        |
| **`pg_trgm` 模糊召回**       | ✅ `similarity()` 直接排序                           | 🟠 相似度排序弱                                 | 规范条款 / 历史缺陷召回                     |
| `timestamptz`                | ✅ 时区语义正确                                      | 🟠 `TIMESTAMP` 有时区与 2038 问题               | 全部时间列                                  |
| 宝塔运维                     | ✅ 软件商店有 PG 管理器；备份用 `pg_dump`            | ✅ **宝塔最强项**（备份/phpMyAdmin）            | 日常运维                                    |
| 我个人的熟悉度               | 🟠 需适应（schema/角色模型、JSONB 语法、标识符小写） | ✅ 我的既有栈                                   | —                                           |

> **学习成本要诚实说**：PG 与 MySQL 在 CRUD 层面差异很小，真正要适应的是三件事 ——
> ① `schema` 与用户/权限模型 ② JSONB 查询语法（`->` / `->>` / `@>`）③ 标识符默认折叠为小写（建表用小写蛇形即可避开）。
> **这是 1–2 天的适应成本，不是项目风险**；而"静默丢数据"是项目风险。

**建议：PostgreSQL 16**，扩展 `pgcrypto`（`gen_random_uuid`）+ `pg_trgm`；PostGIS 暂不装。

## 8. 无论选哪门语言，都要一起做对的 5 件事

| #   | 事项                           | 说明                                                                                                                               |
| --- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **验证发生在服务端**           | 客户端模型是契约，服务端必须按 schema 校验入参（并校验 AI 返回、失败自动重试一次），不静默降级、不静默 mock                        |
| 2   | **迁移从第一天就有**           | 每个 migration 向前兼容（新增列可空、不删旧列）；三处要手写 SQL：部分索引 · GIN（数组/jsonb）· 咨询锁                              |
| 3   | **密码哈希用零原生依赖的实现** | 共机 + 不碰 SSH → 别引入需要编译的东西：Node 用内置 `node:crypto` 的 `scrypt`；Python 用 `hashlib.scrypt`；Go 用 `x/crypto/scrypt` |
| 4   | **结构化日志 + `/health`**     | 没人能上机器看日志，日志必须是可检索的 JSON；`/health` 聚合 DB / OSS / AI 上游                                                     |
| 5   | **组件分阶段加**               | 先只上 PG；Redis / 后台 Worker 有真实压力再加（接口层不用改）                                                                      |

## 9. 讨论时建议一起回答的问题

1. **后端长期由谁维护？**（如果主要是我们两个 + AI，Node 的"AI 最能写"优势就是决定性的）
2. **我们愿意投入学一门新语言吗？**（愿意 → Go 的部署优势才兑现；不愿意 → 直接用 Node 或 Python）
3. **院里有会长期写 Python 的人吗？**（或者我们自己愿意以 Python 为主）
4. **AI 网关留原地还是搬到 node0？**（建议留原地：它服务多个项目，搬动会打断别人）
5. **部署接受哪种形式？**（宝塔进程守护 + PM2/二进制/uvicorn 三选一；都不阻塞原型验证）

> 这 5 条回答之后，语言与部署就能定；而 §6 里"与语言无关"的部分（表结构 / 同步协议 / 接口）
> **现在就可以动手**，不会因为选型改变而返工。
