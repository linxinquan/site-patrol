## 1. 定位

**一句话**：它是**与后端配套的一个前端**，把 App 拿不到的数据录进数据库。

| | 说明 |
|---|---|
| 是什么 | **后台管理界面**，操作者是**开发 / 运营** |
| 谁用 | **操作者**（开发 / 运营），可以只有 1 个人 |
| 服务什么 | **演示版 + 当前这一个项目** |
| 判据 | **没有它，演示和当前项目能不能跑？** 不能 → 做；能 → 不做 |
| 验收标准 | 数据能录进去（App 能否读到 → §9 冒烟测试） |

### 1.1 与 App 的分工

| | 后端操作界面 | App |
|---|---|---|
| 负责 | 项目**开工前的样子** | 现场**正在发生的事** |
| 数据 | 项目档案 · 成员 · 图纸 · 进度 | 缺陷 · 验收 · 量尺 · 巡场 · 报告 |
| 频次 | 一个项目用几次 | 每天用 |

一句话：**这个界面只做「输入」，不做「使用」。**

### 1.2 本版的定位改变：不做项目管理 Web

上一版要做的是**项目管理 Web**（超管 / 项目负责人 / 成员三层角色、代操作留痕、权限矩阵、统计与审计）。**本版不做。**

原因一句话：**注重演示版顺利进行 —— 没有真实使用者使用的界面，不值得做。**

> ⚠️ 区分清楚：**不做项目管理 Web ≠ 不录成员数据。**
> `memberships` **一定要录**（见 §3）—— App 靠它判断"登录后能看到哪些项目"。
> 那是**给 App 用的数据**，不是给人开后台账号。

> ⚠️ 同理：**有「角色管理」页（页面 6）≠ 回到角色化界面。** 两者的分界是：
>
> | | 做 | 不做 |
> |---|---|---|
> | **角色数据** | **录进去**：角色有哪些、各自能做什么（页面 6）；谁担任什么角色（页面 3） | —— |
> | **界面自身** | —— | 按角色隐藏菜单 / 按钮 / 数据 |
>
> 一句话：**角色是「数据」，不是这个界面的「形态」。**
> 本界面只有 1 个登录账号、无角色可依 → 界面自身永远不做角色化；
> 而角色数据必须有录入入口，否则后端权限校验（架构文档 §3.1）没有任何数据可用。

## 2. 使用者与工程形态

### 2.1 使用者

| | |
|---|---|
| 谁 | **开发 / 运营**（操作者），可以只有 1 个人 |
| 账号 | **只有一个管理员账号**（账号 + 密码；不做注册 / 找回；**后台自身不分角色**） |

> 成员账号是**数据**、不是后台账号（见 §4.3）—— 后台登录账号只有一个。
> ⚠️ 这里的"不分角色"说的是**后台这个账号自己**；页面 6 管的是**业务角色**（App 端成员的角色），两者无关。

### 2.2 仓库与部署形态

**本界面与业务后端分属两个仓库。** 前后端各自独立成仓、各自出镜像，在集群里汇到同一个域名。

```
site-patrol-admin/          ← 本界面（前端独立仓库，Vue 3 + Vite）
  ├─ src/
  │    ├─ views/            6 个页面：登录 / 项目列表 / 成员 / 图纸 / 进度 / 角色管理
  │    ├─ api/              接口调用（类型由 openapi.json 生成，见 §2.3）
  │    └─ router/           前端路由（hash 模式，不带 `/admin` 前缀，见 §4.0）
  ├─ Dockerfile             ← 构建静态产物 + 静态托管（无服务端逻辑）
  └─ package.json

site-patrol-backend/        ← 业务后端（Python 3.12 + FastAPI）
  ├─ app/                   FastAPI 应用（接口清单见 BACKEND_ARCHITECTURE.md §13）
  ├─ migrations/            Alembic
  ├─ Dockerfile
  └─ .env                   本地开发用；线上走 k8s Secret，**不入库**
```

> ⚠️ **别把仓库名搞混**：`site-patrol`＝Flutter App · `site-patrol-backend`＝**业务后端**（本界面调的就是它）· `site-patrol-admin`＝**本界面**。

| # | 约定 | 原因 |
|---|---|---|
| 1 | **前端独立仓库**（`site-patrol-admin`） | 两种语言两套工具链（`uv` vs `npm`），混一个仓会让 CI 与 clone 都变重 |
| 2 | **Vue 3 + Vite + vue-router**（最小配置） | 页面会长到 15+，且**角色登录是已确认的未来方向**（§8.2）；表格与多行表单用绑定比手写 DOM 省数倍 |
| 3 | **路由用 hash 模式**（`#/login`）；Vite `base` 设 `/admin/` | 不需要 Ingress 为前端配 404 fallback —— 少一个要和运维沟通的点；`base` 不设会白屏（§4.0） |
| 4 | **各自独立镜像**：`api`（FastAPI）· `admin`（静态产物） | 前后端**独立发布、独立回滚** —— 这正是分仓要换来的东西 |
| 5 | **Ingress 按路径分流**（`/api/*` → api；`/admin/*` → admin） | 同一个域名、同一张证书，对使用者仍是一个地址 |
| 6 | **接口基址写相对路径**（`/api/v1/...`） | 不带 host —— 域名或端口变化不用改前端 |
| 7 | **契约以 OpenAPI 为准**（§2.3） | 分仓后不再"同一次提交"，靠契约对齐 |

> ❌ **不要走这条路**：让后端 CI 跨仓拉前端产物、打进后端镜像。
> 那等于分了仓却没拿到独立发布，反而多一层跨仓耦合 —— 不如干脆别分。

> **部署（09-22 定）**：k8s，由团队内运维成员执行（`BACKEND_ARCHITECTURE.md` §14）。
> 前端镜像**只是静态文件 + 静态托管** —— 无数据库、无服务端逻辑、除探针外不需要任何集群特性；
> 后端镜像才是无状态服务（约束见 `BACKEND_ARCHITECTURE.md` §14.2）。

### 2.3 接口契约与开发顺序

**FastAPI 的 `/openapi.json` 是从代码推导出来的，不是另写一份文档。** 推导来源＝路由上的**请求 / 响应 Pydantic 模型** —— 所以顺序是硬的：

```
① 表结构（已定：BACKEND_ARCHITECTURE.md §7）
      ↓
② Pydantic 模型（每个接口的请求 / 响应形状）   ← 契约在这一步成型，后端落地
      ↓
③ /openapi.json（自动产出，不手写）
      ↓
④ 前端生成 types.ts（openapi-typescript）
```

| # | 纪律 | 说明 |
|---|---|---|
| 1 | **前端不手写字段名** | `types.ts` 由 `openapi.json` 生成。手抄字段名＝分仓后必然发生的第一类事故 |
| 2 | **改 schema ＝ 改契约** | 后端改字段后**必须通知前端重新生成**，且两仓在同一个发布窗口内改完 |
| 3 | **ORM 模型 ≠ Pydantic 模型** | SQLAlchemy 管表、Pydantic 管接口形状，是两套。用 `from_attributes=True` 从 ORM 对象直接序列化，**不要手写第三套映射** |

**⚠️ 这不等于"前端要等后端写完"。** 正确做法是**后端先只写骨架**：

> 路径 + Pydantic 模型 + 返回 `501` → `/openapi.json` 就出来了 → 前端照它生成类型、把页面写完 → 后端再填实现。

**前端开工的最小前提，是「它第一个页面用到的那几个接口」的模型已定**（登录 + 项目列表 + 建项目），**不是全部接口**。

**前端构建怎么拿到 `openapi.json`**：建议后端在 CI 里把它导出为构建产物，前端构建时取用 —— 这样前端构建**不依赖后端是否在运行**。
生产环境的 `/docs` 建议关掉（FastAPI `docs_url=None`），`/openapi.json` 是否对外由后端定。

## 3. 要录入的数据（核心章节）

**界面的唯一目的就是把这些数据录进去。** 每个实体都标出**消费方**（App / 服务端）—— **没有消费方的字段不要录**。例外只有一处（角色），理由见 §3.2。（库内字段名见 `BACKEND_ARCHITECTURE.md`，本文只写业务名。）

### 3.1 数据清单（9 类）

| # | 实体 | 主要字段 | 消费方 |
|---|---|---|---|
| 1 | **账号** | 姓名 / 手机号 / 单位 | 登录、成员显示、报告署名 |
| 2 | **项目** | 名称 / 甲方 / 地点 / 状态 / 场地面积 / 建筑面积 / 床位 / 设计概念 | 引导页选项目、首页项目卡、报告封面 |
| 3 | **参与方** | 角色 / 单位 / 联系人 / 职务 | 首页项目信息、报告抬头 |
| 4 | **里程碑** | 名称 / 日期 / 是否完成 | 首页进度时间轴、报告"施工进度"章节 |
| 5 | **成员** | 用户 / 角色 / 专业 | **可见性判定**（登录后能看到哪些项目）+ 权限点下发 |
| 6 | **图纸** | 名称 / 专业 / 楼栋 / 楼层 / 版本 | 图纸 tab 目录、拍照验收选部位、量尺选图纸 |
| 7 | **底图** | 底图文件 + 像素宽高 | 图纸查看、图上打点 |
| 8 | **施工进度** | 里程碑状态 / 日期 / 备注 / 照片 | 首页进度时间轴 |
| 9 | **角色** | 角色名 / code / 说明 / **权限点** | **服务端权限校验**（架构文档 §3.1）· 成员页下拉的选项 |

> 第 5 行的「角色」是**引用**，第 9 行才是**定义** —— 成员录的是 `role_code`，角色表录的是这个 code 有什么权限。
> 第 1 行「账号」与第 9 行「角色」不要混：**账号是「谁」，角色是「能做什么」**。
> 第 3 行「参与方」里的角色也不是第 9 行 —— 那是**抬头角色**（甲方 / 监理 / 总包），只用于报告正文。

### 3.2 三条录入纪律

| # | 纪律 | 原因 |
|---|---|---|
| 1 | **没有消费方的字段不录** | 录了没人读 = 白做界面 + 白占字段。⚠️ **唯一例外是「角色」**：消费方是**服务端校验**（不是 App、也不是本界面）—— 但权限模型已定（架构文档 §5.5），不录 = 后端那套权限没有数据可依 |
| 2 | **表结构按 `BACKEND_ARCHITECTURE.md` 建全** | 界面可以只填 3 个字段，表要建全。**界面易改，表难改** |
| 3 | **`memberships` 一定要录** | 不录 → App 登录后看不到任何项目（**最容易漏的一条**） |

## 4. 页面清单

**6 个页面，全部挂在同一个入口下。**

| # | 页面 | 前端路由 | 页面目标 | 主要区块 | 核心操作 |
|---|---|---|---|---|---|
| 1 | 登录 | `#/login` | 进得去 | 账号 + 密码 | 登录 |
| 2 | 项目列表 | `#/projects` | 找到已有项目 / 建新项目 | 项目表（名称 / 状态 / 成员数 / 图纸数）+ 新建按钮 | 新建、进入项目、**进角色管理** |
| 3 | 项目 · 成员 | `#/projects/:id/members` | 决定"谁能看到这个项目" | 成员表（姓名 / 手机号 / 单位 / 角色 / 专业）+ 加人表单 | 加人、改角色、移除、就地建号 |
| 4 | 项目 · 图纸 | `#/projects/:id/drawings` | **让 App 有图可用** | 图纸表（名称 / 专业 / 楼栋 / 楼层 / 版本 / 状态）+ 上传区 | **上传**、改名称与楼层、上传新版本、删除、发布 |
| 5 | 项目 · 进度 | `#/projects/:id/progress` | 让 App 首页有进度可显示 | 里程碑列表 + 回填表单 | 逐条回填（状态 / 日期 / 备注 / 照片） |
| 6 | **角色管理** | `#/roles` | 让「角色 → 权限点」有地方可录 | 角色表（角色名 / code / 权限点数 / 在用人数 / 类型）+ 权限点勾选 | 新增角色、改权限点、改名与说明、删除 |

**导航结构**：

```
登录 → 项目列表 ─┬─（点进）项目详情 → 3 个 tab：成员 / 图纸 / 进度
                 └─（顶部入口）角色管理
```

**层级 2 层**，任一页面 ≤2 次点击可达。

> **作用域**：页面 2~5 在**项目**下（路由带 `:id`）；**页面 6 是全局页** ——
> `roles` 表没有 `project_id`（架构文档 §2.3），角色跨项目共用，所以它**不能**挂在 `/projects/:id/` 下。

### 4.0 地址怎么拼（三个概念别混）

| 概念 | 值 | 谁决定 | 说明 |
|---|---|---|---|
| **访问路径** | `/admin` | 运维的 Ingress 规则 | 决定"从哪个地址进来"；**不进前端路由表** |
| **前端路由** | `#/login` … `#/projects/:id/progress` · `#/roles` | 前端 `router/` | 路由表里写 `/login`，**不带 `admin` 前缀** |
| **静态资源前缀**（Vite `base`） | `/admin/` | 前端 `vite.config` | ⚠️ **必须设** —— 不设则 JS / CSS 请求 404，页面白屏 |
| **完整地址** | `https://<域名>/admin/#/projects` | 三者拼起来 | hash 模式：`#` 之前是部署路径，之后才是路由 |

> **路由表里不写 `/admin` 前缀** —— 那是部署位置，不是页面层级。
> 将来换路径（如 `/console/`）只改 Ingress 与 Vite `base`，路由表一行不动。
> 用 hash 模式的原因见 §2.2 约定 3。

### 4.1 通用约定（6 个页面都要有）

| # | 约定 | 说明 |
|---|---|---|
| 1 | **四态齐全** | 空（还没数据）· 加载中 · 失败（可重试）· 超限（超长文本 / 超多行） |
| 2 | **破坏性操作二次确认** | 删除图纸、删除版本、删除成员、删除里程碑 |
| 3 | **提交有明确反馈** | 成功 / 失败都要说清"哪一条失败了、为什么"，不吞成"提交失败" |
| 4 | **必填与格式前端先拦一道** | 服务端仍会校验，**以服务端为准**，422 明细要展示出来 |

### 4.2 页面 2 · 项目列表 + 新建

| 区块 | 字段 |
|---|---|
| 基本信息 | 名称 / 甲方 / 地点 / 状态 / 场地面积 / 建筑面积 / 床位 / 设计概念 |
| 参与方 | 角色 / 单位 / 联系人 / 职务（可增删行） |
| 里程碑 | 名称 / 日期（6~10 行，来自施工组织设计的总进度计划） |

- **表单式录入，不做向导**（字段不多，向导只增加点击）
- 提交后跳转到项目详情。**里程碑在这里录，因为它是页面 5 进度回填的框架。**

### 4.3 页面 3 · 成员

| 区块 | 说明 |
|---|---|
| 列表 | 姓名 / 手机号 / 单位 / 角色 / 专业 |
| 加人 | 从已有账号中选；**搜不到 → 就地填「姓名 + 手机号 + 单位」建号** |
| 角色 | 下拉选择；**选项从角色表拉（页面 6）**，不硬编码 |
| 移除 | 允许；不设"最后一个负责人"这类约束（**本界面自身不分角色**，§1.2） |

> **这个页面的作用只有一个**：让 App 知道"谁能看到这个项目"。不是给别人开后台账号。

> ⚠️ **角色下拉的数据源变了**（09-22）：原来写"3 个选项"，现在角色可维护（页面 6）——
> 硬编码 3 项会让**新建的角色在成员页选不到**。所以下拉取角色表全量；
> 表单**默认选中「驻场工程师」**（对齐 App 使用者），常用角色仍是一次点击就选完。

### 4.4 页面 4 · 图纸

| 区块 | 说明 |
|---|---|
| 列表 | 名称 / 专业 / 楼栋 / 楼层 / 当前版本 / 状态（已发布 / 未发布） |
| **上传** | PDF 或图片；文件名 = SHA256（见 §5） |
| 编辑 | 名称、专业、楼栋、楼层（楼层只是标签，**不建楼层表**） |
| 版本 | 上传新版本 → 旧版本自动锁为只读，**历史版本可查、不覆盖** |
| 删除 | 二次确认；**已发布的版本不允许删除**（历史缺陷指向它） |
| 发布 | 显式动作，**上传 ≠ 生效**（见 §5） |

### 4.5 页面 5 · 进度

- 按里程碑**逐条**填：状态（未开始 / 进行中 / 已完成）+ 完成日期 + 备注 + **照片（支持上传）**
- 来源标记为「**后台录入**」
- 界面**不**显示"施工方自报"字样 —— 那是将来免登录分享页才有的来源，两者不得混标

### 4.6 页面 6 · 角色管理

**一句话**：让「角色 → 权限点」这个映射有地方可录。映射存在 `roles.permissions`（架构文档 §3.1）—— 不在这里录，就只剩"改数据库"一条路。

> ⚠️ **它不在演示链路上**（§7.1 那条链不经过它）—— 它是**权限数据的录入入口**：
> **不加它，演示照样跑；可不加它，权限数据就没人录。** 这一点与页面 3~5 不同。

| 区块 | 说明 |
|---|---|
| 列表 | 角色名 / code / 说明 / 权限点数（`12 / 24`）/ 在用人数 / 类型（内置 · 自定义） |
| 新增 | 角色名 + code（英文短名，唯一，**建后不可改**）+ 说明 + 权限点 |
| 编辑 | 同上；code 置灰 |
| 删除 | 二次确认；**只对「自定义 + 无人使用」开放** |

**权限点选择器** —— 这一页唯一有设计含量的地方：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A · 单角色编辑**（推荐） | 打开一个角色 → 权限点按模块分组的复选框 | 改动边界清晰；一次一条记录，保存失败好归因 |
| B · 矩阵表 | 行＝权限点、列＝角色（＝架构文档 §5.5 的形态） | 一眼看全貌，但"保存整张表"语义模糊、部分失败的提示难写 |

界面结构（方案 A）：

```
角色表（初始 7 行）
  └─「编辑」→ 右侧抽屉
       ├─ 角色名 · 说明 · code
       └─ 权限点（按模块分组，清单来自 GET /permissions）
            缺陷   ☐ defect.create   ☐ defect.reply   ☐ defect.update   ☐ defect.assign
            图纸   ☐ drawing.read    ☐ drawing.manage ☐ drawing.calibrate
            成员   ☐ member.manage   ☐ user.create
            …
```

**4 条硬约束**：

| # | 约束 | 原因 |
|---|---|---|
| 1 | **权限点只能勾，不能手输** | 权限点是代码里硬编码的（架构文档 §3.1）；手输拼错 = **存进库里但永不生效，且不报错** |
| 2 | **权限点清单从接口拉**（`GET /permissions`：code + 中文名 + 分组 + 排序） | 中文名与分组是**显示用**的 —— 前端不该抄一份，库里也不该存一份 |
| 3 | **内置角色（`is_system`）不可删、不可改 code** | 它们与既有数据绑定（`memberships.role_code` 已指向它） |
| 4 | **有成员在用的角色不可删** | 删了 → 那些 `memberships.role_code` 指向空，权限**静默失效** |

**`admin` 这一行特殊**：列表里可见，但**只读** —— 它是操作者自身、权限固定为全部。让它可编辑，等于可能把自己锁在外面。

**改完立即生效**：`role` 不放 JWT（架构文档 §3.1）→ 下一次请求就按新权限判，不用重登、不用等 token 过期。

**这一页不负责什么**：不做角色化界面（§1.2）· 不做专业过滤（第一版只按权限点放行，架构文档 §3.1）。

## 5. 图纸这条链路（核心）

**整个界面的价值都压在这里。** 其余页面是脚手架；这条链断了，App 什么都做不了。

**本界面只负责一件事：让 App 有图可用。图纸校准不在本版范围。**

### 5.1 三步

```
① 上传 PDF（或图片）
     → 直传 OSS（文件名 = SHA256）
     → 出底图（供前端渲染的图片 / 缩图，走 x-oss-process，服务端不做图）
② 填图纸信息：名称 / 专业 / 楼栋 / 楼层
③ 发布（显式动作，不是上传即生效）
     → 该版本成为 App 的默认版本
App 端：重新拉底图
```

### 5.2 硬约束

| # | 约束 | 原因 |
|---|---|---|
| 1 | **只收 PDF / 图片**，不收 DWG | DWG 交给设计院出图流程，解析成本高且本版不需要 |
| 2 | **图纸文件不做压缩** | ⚠️ **与现场照片规则相反**：照片压到长边 2048px；**图纸压了精度就废、坐标全错** |
| 3 | **版本号必填** | 图纸改版后，无版本的历史坐标会静默错位 |
| 4 | **已发布的旧版本锁定只读** | 历史缺陷仍指向旧版本，不能错位 |
| 5 | **记录底图像素宽高** | App 直接读它换算坐标；缺了就画不出点位 |

### 5.3 发布后要发生的事

| 对象 | 动作 |
|---|---|
| App | 提示「图纸已更新，请重新加载」→ 重拉底图 |
| 旧版本 | 锁为只读，历史缺陷仍指向它（**不错位**） |
| 新版本 | 成为默认版本 |

## 8. 红线与后续触发条件

### 8.1 红线（不是"不做"，是"不许做错"）

| # | 红线 | 原因 |
|---|---|---|
| 1 | **没有版本号的图纸不允许发布** | 改版后无版本的历史坐标会静默错位 |
| 2 | **发布是显式动作，不是上传即生效** | 可能有人正在用旧图打点，中途换底图会造成新旧混用 |
| 3 | **不做自动坐标迁移** | 算法不可靠且不可解释；旧版本锁定只读，历史坐标本就没错位 |
| 4 | **不碰业务数据** | 缺陷、验收、报告归 App；两边都写同一张表必然冲突 |
| 5 | **不做 AI 结论的最终裁决** | AI 只出建议，人确认后才生效（与 App 端一致） |
| 6 | **图纸文件不压缩** | 与现场照片规则相反，见 §5.2 |
| 7 | **表结构按 `BACKEND_ARCHITECTURE.md` 建全** | 界面可以简陋，表不能简陋 |
| 8 | **已发布的图纸版本不允许删除** | 历史缺陷指向它，删了历史就断链（删除只对未发布版本开放） |
| 9 | **权限点只能勾选，不允许手输** | 权限点是代码里硬编码的（架构文档 §3.1）；拼错 = 存进库里但**永不生效，且不报错** |
| 10 | **内置角色与在用角色不允许删除；`admin` 行只读** | 删了 → 成员的权限悬空；`admin` 可编辑 = 可能把自己锁在外面 |

### 8.2 什么时候重新考虑"做成管理后台"

**已确认的方向（09-22）：未来版本要支持其他角色登录。** 本版不做，但**表结构与接口不为它设障**。

> ⚠️ 注意区分：**页面 6（角色管理）已经把「角色数据」这块提前做了** —— 那是**数据录入**；
> 本节说的是**角色化界面**（按登录者角色隐藏菜单 / 按钮 / 数据）。**两者不是一回事**（§1.2）。

什么时候做，看下面任一条先出现（说明角色和协作**真实存在**了）：

| # | 触发条件 |
|---|---|
| 1 | 第 2 个真实项目上线（不再是一人项目） |
| 2 | 出现第 2 个操作用户，且需要区分"能做什么" |
| 3 | **负责人或驻场主动说"我要自己上传图纸 / 自己看统计"**（最可能先发生的） |
| 4 | 需要回答"这条数据是谁录的"（合规或纠纷） |

那时要补的是：`created_by` 留痕、**按角色的界面裁剪**、统计视图。
（**权限点校验本版已在后端就位**——架构文档 §3.1；缺的是"界面按它裁剪"这一步。）**表结构本版已建全，不会返工。**

## 9. 冒烟测试（可现场跑一遍）

**这是端到端冒烟测试，覆盖三方：本界面 + 业务后端 + App。**
本界面的责任范围是 **V1~V4、V6、V7 中「数据录进去」的那一段**；V5 的主体是**业务后端 × App**（见 §6）。

| # | 步骤 | 通过标准 | 主要归属 |
|---|---|---|---|
| V1 | 操作者登录 | 能登录；错误密码被拒 | 本界面 |
| V2 | 新建一个项目（基本信息 + 里程碑） | 项目出现在列表；里程碑能增删；字段在 App 端能读到 | 本界面 |
| V3 | 添加 2 名成员（其中 1 名系统里没有） | 两人都进项目；不存在的那位走"**就地建号**" | 本界面 |
| V4 | **上传一张 PDF 图纸 → 填名称与楼层 → 发布** | 底图能预览；未填名称 / 版本不允许发布；发布后旧版本自动锁只读 | 本界面 |
| V5 | **App 端登录成员账号 → 打开图纸 → 打点** | **只看到这个项目**；看到的是**刚上传的那张**（不是预置图）；点位落在图上并按底图像素坐标保存 | 业务后端 × App |
| V6 | 按里程碑回填一条进度 | 能保存并回显；App 首页进度时间轴能看到 | 本界面 |
| V7 | 在角色管理改一个角色的权限点并保存 | 保存后重进回显一致；该角色在成员页下拉里能选到 | 本界面 |

> **V4 + V5 是命门** —— 它验证的是「**界面传的图 = App 用的图**」，也就是图纸链路真的通了。
> 其余 5 条是脚手架。

> V7 **只验到"录进去、能被引用"为止** —— App 端第一版不消费权限点（§4.6），
> 所以没有"改完权限 App 端行为跟着变"这一步可验，别把它当端到端。

**7 条全过 = 冒烟通过，演示版成立。**

**没过时怎么归口**（避免"整条链一起查"）：

| 卡在哪 | 先查哪里 |
|---|---|
| 页面打不开 / 白屏 | Ingress 路径与 Vite `base`（§4.0） |
| 接口 4xx、字段对不上 | `openapi.json` 契约 —— 前端需重新生成类型（§2.3） |
| 界面提交成功、App 读不到数据 | 业务后端 × App 的联调范围，**不是本界面** |
| App 读到的还是预置图 | App 侧数据源未切换（§6） |
| 成员页角色下拉是空的 | 角色表没数据 → 先跑页面 6，或后端 seed（§4.6） |
| 权限点勾了却没生效 | 权限点 code 拼错（§4.6 约束 1）；或 **App 端第一版本就不消费权限点** |

## 10. 实现约定

| # | 约定 | 说明 |
|---|---|---|
| 1 | **前端独立仓库、独立镜像** | `site-patrol-admin`；k8s 下 Ingress 按路径分流（§2.2） |
| 2 | **Vue 3 + Vite + vue-router**，hash 模式；`base` 设 `/admin/` | 页面会长到 15+，且角色登录是已确认方向（§8.2）；`base` 不设会白屏（§4.0） |
| 3 | **类型由 OpenAPI 生成，不手写字段名** | 分仓后唯一的契约保障（§2.3） |
| 4 | **服务端留一个权限校验函数** | 本界面调用的接口**恒放行**（操作者＝全部权限）；函数按 `roles.permissions` 实现即可 —— 将来 App 端角色登录时它已在位（架构文档 §3.1）。**本界面自身不按角色隐藏任何东西**（§1.2） |
| 5 | **不做"只有演示才需要"的功能** | 如一键填充演示数据 —— 做完就会变成依赖 |
| 6 | **权限点清单从 `GET /permissions` 拉** | 前端不硬编码权限点与其中文名；库里也不存显示名（§4.6 约束 2） |
