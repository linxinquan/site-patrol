## 1. 定稿结论

| 层                  | 定稿                                                   | 一句话理由                                                                                                                                                |
| ------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **语言 / 框架**     | **Python 3.12 + FastAPI**                              | 见 §2 —— `Pydantic v2` 把「客户端模型即契约 + AI 返回落库」表达成同一套模型：**AI 写错会在启动或请求时直接报错，而不是静默降级**                          |

| **对象存储**        | **阿里云 OSS · 华南1（深圳）· 私有读**                 | 与集群同地域 → **内网读免费**；缩图走 `x-oss-process`（服务端不做图）                                                                                     |
| **依赖管理**        | **`uv` + `pyproject.toml`**（锁文件 `uv.lock`）        | 零原生依赖 → 镜像构建确定、可复现                                                                                                                         |
| **部署**            | **k8s**                                                | 集群 / Ingress / 证书 / PG 实例 / 备份**不在应用侧范围**；应用侧（研发）交付**两个镜像**（`api` / `admin`）+ 配置项清单                                  |
| **前端 / 静态页**   | **独立仓库 + 独立镜像**（`site-patrol-admin`）         | **Vue 3 + Vite**；Ingress 按路径分流（`/api/*` → api，`/admin/*` → admin）→ 前后端独立发布与回滚；契约靠 `openapi.json`                                  |

**一句话总结**：**Python + FastAPI + PostgreSQL + OSS，打成两个镜像（`api` + `admin`），跑在 k8s 上。**

## 2. 为什么是 Python

**一个前提**：本项目**主要靠 AI 辅助开发**，所以判据权重与「有专业后端团队」的情况不同。

| #     | 判据                 | 说明                                                          |
| ----- | -------------------- | ------------------------------------------------------------- |
| 1     | AI 能多准地写它      | 语料越厚、范式越标准，生成与自我纠错越可靠                    |
| 2     | 出错时搜得到答案     | 生态资料量直接决定「卡住多久」                                |
| **3** | **工具链能替你查错** | **决定性判据** —— 决定「AI 写错了会不会被拦住」               |
| 4     | 与已有资产对齐       | 客户端模型（Dart 强类型）即契约，服务端模型要能与之逐字段对应 |
| —     | 性能 / 并发 / 内存   | **本项目 QPS 极低，不作判据**（瓶颈在 PG 与 OSS 外网流量）    |

**决定性理由（判据 #3）**：本项目的数据形态是「**客户端模型即契约**」——
`lib/data/models/` 的 `toJson/fromJson` **唯一决定**落库形态，服务端只做校验 + 原样落 jsonb。
`Pydantic v2` 让**请求/响应模型**与**AI 返回结果校验**用同一套模型表达，
于是 AI 写错会在**启动或请求时直接报错**，而不是静默降级；一次静默错数据就要人工回补。

**附带收益**：FastAPI 自动生成 OpenAPI 文档，客户端（Dart）可直接据此校对请求模型。

## 3. 数据库 = PostgreSQL（硬结论）

**这条不是偏好问题 —— 选错了会让客户端静默丢数据。**

### 3.1 硬理由：变更流的序号分配

离线同步靠一张变更流表 + 游标：`changes(seq bigserial, …)`，客户端只记一个游标，按 `seq > cursor` 拉增量。

**陷阱**：`bigserial` 的**分配**严格递增，但**可见性由提交时间决定**。两个事务可能「先分配、后提交」：

```
T1  事务 A  nextval → seq = 100（未提交）
T2  事务 B  nextval → seq = 101，随后提交
T4  客户端拉取，读到 max(seq) = 101 → 游标推到 101
T5  事务 A 提交，seq = 100 才可见
T6  客户端从 101 继续拉 → 100 永远拉不到（静默丢一条变更，无任何报错）
```

**解法（1 行）**：在写 `changes` 的**同一事务开头**取**事务级咨询锁**，把序号分配串行化，
使「分配顺序 ≡ 提交顺序」，`seq > cursor` 恢复正确：

```sql
SELECT pg_advisory_xact_lock(981001);   -- 事务结束自动释放，不会泄漏
INSERT INTO changes(project_id, entity, entity_id, op) VALUES (...) RETURNING seq;
```

代价：变更流写入被串行化。本项目写入 QPS 极低，**代价可忽略**。**建表即带上。**

> 事务级锁是关键 —— 它随事务结束自动释放，连接池下不会泄漏、不会误释放。

### 3.2 落地口径

- **实例待提供**（托管实例或集群内 Operator）；应用侧**只依赖 `DATABASE_URL`** 一个环境变量 → 换实例不改代码。
- **不锁版本**；需支持：`pg_advisory_xact_lock` · `gen_random_uuid` · `pg_trgm`。
- 扩展：`pgcrypto`（`gen_random_uuid`）+ `pg_trgm`；**PostGIS 暂不装**。
- **写 SQL 时会用到的 PG 能力**：`text[]` + GIN · jsonb 一等类型 + GIN · 部分索引 · `ON CONFLICT DO NOTHING`（幂等 upsert）· `pg_trgm` 模糊召回 · `timestamptz`。
